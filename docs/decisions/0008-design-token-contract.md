# 0008 — Design tokens flow one way, from Nix into Rust

Status: accepted (closes Block 0 open question 7)

## Context

`design/v1.nix` is intentionally empty and `neptune-design` is an empty crate.
That is fine while nothing has a colour, a spacing value, a corner radius or an
animation duration. Shader work is the first thing that will want such values,
and the path of least resistance there is to type a constant next to the code
that uses it. Once a few of those exist, the same value is copied in three
places, they drift, and there is no longer any one answer to "what is the
accent colour" or "how long is the open animation".

This decision defines the contract before any token exists, so that the first
one is authored correctly rather than migrated later. It defines the contract
only: no tokens are populated and no generator is written.

## Options considered

1. **Generate the Rust at build time into `OUT_DIR` via `build.rs`.** The
   generated code is never stale and Nix is a hard build dependency. But the
   tokens stop being reviewable in the source tree — a diff to a colour is
   invisible — and every build needs the generator to succeed.
2. **Generate a committed Rust file from `design/v1.nix` as an explicit step.**
   Diffs to design values are visible in the generated file and reviewed like
   any other code, and a plain cargo build needs no Nix beyond the normally
   pinned inputs. The cost is that the generated file can be stale; this is
   caught later by a check that regenerates and compares.
3. **No generation: hand-write the tokens in `neptune-design` and keep
   `design/v1.nix` as documentation.** Two sources for every value again, with
   no mechanism keeping them equal. Rejected outright.

## Decision

Option 2. The contract is:

**What `design/v1.nix` owns.** The authoritative design values for design
version 1: every name, value, unit and short semantic note (what it is for).
It is the only place a design value is authored. A version is a frozen set:
changing an existing value's meaning under the same version is not allowed;
such a change belongs to `v2.nix`.

**What generates from it.** A generator, not yet written, reads `design/v1.nix`
and emits Rust. The generator and the Nix file are the only authored inputs;
nothing else contributes.

**Where the output lands.** Exactly one generated module inside the
`neptune-design` crate (for example `crates/neptune-design/src/generated.rs`),
carrying a header stating that it is generated from `design/v1.nix` and must
not be edited by hand. It is committed, so a design change is reviewable as a
normal diff, and regenerated by an explicit command. `build.rs`/`OUT_DIR` is
rejected for the reason above.

**Who may read it.** `neptune-design` is the sole owner and re-exporter of the
tokens. Every other crate — the compositor, `neptune-scene`, later crates —
reads design values only through `neptune-design`'s public API. No other crate
may read `design/v1.nix`, read the generated module directly, or define a
design value.

**What is forbidden.** Hand-written design constants anywhere in the source
tree: colours, spacings, sizes, radii, border widths, typography, opacity, or
animation durations, whether as named constants or inline literals, in any
language. A new design value is added to `design/v1.nix` and regenerated; it is
never introduced at the point of use.

**Boundary.** A value is a token if it is a design choice a human could
reasonably want to change on its own. Algorithmic constants — a matrix epsilon,
a loop bound, a byte size — are not tokens and stay with the code that needs
them. When a value is genuinely both, it is documented as one.

## Consequences

- The first shader or layout code that needs a design value must first write
  the generator and populate `design/v1.nix`. Until then there are no design
  constants, which is consistent with Block 0 having no rendering.
- `neptune-design` becomes the single public surface for presentation values,
  so a colour is changed in one authored place.
- The contract is not yet enforced: the generator, the regeneration command and
  the staleness check do not exist. Until they do, the rule holds by
  convention, and this ADR is the reference for what is allowed.
- Committing generated output keeps design changes visible in review, at the
  cost of a possible stale file, which the future check exists to catch.
- Design versioning is explicit: a semantic change is a new `vN.nix`, not an
  edit to a frozen one.
